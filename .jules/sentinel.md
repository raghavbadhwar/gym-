## 2026-03-29 - Fixed Webhook Signature Verification and Timing Attack
**Vulnerability:** The WhatsApp webhook endpoints (`/whatsapp`) lacked critical security mechanisms. The `GET` verification endpoint used a standard string equality (`==`) comparison, making it vulnerable to timing attacks. More importantly, the `POST` endpoint accepted incoming messages blindly without verifying the `X-Hub-Signature-256` payload signature, allowing any attacker to forge messages and impersonate Meta/WhatsApp. Furthermore, potential internal exceptions were being swallowed and returned as 200 OK, failing open instead of failing secure.
**Learning:** Webhook endpoints must explicitly authenticate incoming payloads using the cryptographic signature provided by the service (e.g., HMAC-SHA256). Additionally, any string comparison involving tokens, hashes, or secrets must use constant-time operations like `hmac.compare_digest` or `secrets.compare_digest` to prevent token brute-forcing via timing side-channels. Exception handlers should be layered so that intentional HTTP errors (like 401 Unauthorized or 500 Server Error) propagate to the client and avoid returning a deceptive 200 OK status on failure.
**Prevention:** Always require and validate cryptographic signatures on public-facing webhooks before processing the payload. Use `secrets.compare_digest` for token comparisons. Implement "fail secure" designs by ensuring that unconfigured secrets or invalid signatures result in explicit HTTP error codes rather than default success statuses.

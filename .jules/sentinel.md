## 2025-02-28 - [CRITICAL] Webhook Signature Validation and Timing Attacks
**Vulnerability:** The application was not verifying the payload signature (`X-Hub-Signature-256`) from Meta webhooks, allowing anyone to spoof messages to the endpoint. Furthermore, the webhook verification endpoint compared verification tokens using standard string equality, which is vulnerable to timing attacks. Finally, an overly broad `except Exception as e:` block swallowed all errors (including potential validation failures) and returned a 200 OK, failing open rather than securely.
**Learning:** Webhook endpoints must explicitly validate the cryptographic signature of incoming payloads to ensure authenticity. In Python, comparing secrets using `==` is unsafe; `secrets.compare_digest` or `hmac.compare_digest` must be used to prevent attackers from inferring the secret token character by character through response timing analysis. When a critical configuration value (like an app secret) is missing, the application should "Fail Secure" (e.g., raise a 500 error) rather than bypassing the check. Exception handlers in API routes must be careful not to catch and swallow intentional HTTP errors (like 401 Unauthorized), which can cause the application to improperly signal success to external services.
**Prevention:**
1. Always enforce `X-Hub-Signature-256` validation on incoming payloads from Meta webhooks using HMAC-SHA256 and `hmac.compare_digest`.
2. Always use `secrets.compare_digest` when verifying secrets like `hub_verify_token`.
3. Implement a "Fail Secure" strategy by explicitly checking for the presence of required configuration secrets and raising a 500 error if they are missing.
4. Catch and re-raise `HTTPException` before general `Exception` handlers in FastAPI routes to ensure intentional HTTP error codes are correctly returned to the client.

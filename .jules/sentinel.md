## 2026-04-25 - Webhook Signature Validation & Timing Attacks
**Vulnerability:** The WhatsApp webhook receiver endpoints were lacking critical cryptographic validation. The POST endpoint failed to verify the `X-Hub-Signature-256` payload signature against a secret, allowing any unauthorized third party to spoof webhook events (like fake messages or booking requests). Additionally, the GET endpoint used the `==` operator to compare the `hub.verify_token`, exposing it to timing attacks where an attacker could incrementally guess the token by measuring request response times. Finally, a broad `except Exception:` block would catch `HTTPException` validation errors and mistakenly return `200 OK` (a fail-open state).
**Learning:** In fast-moving development, standard Python equality (`==`) is often used intuitively for token verification without realizing it short-circuits upon the first mismatched byte, creating timing leaks. Furthermore, broad exception handlers designed to "prevent Meta from retrying" can accidentally swallow intended security rejections (like `401 Unauthorized` or `403 Forbidden`), tricking both the developer and the system into believing a request was successfully processed. Payload bodies must also be hashed using raw bytes (`await request.body()`) before JSON parsing, as parsing alters the byte representation and causes hash mismatches.
**Prevention:** Always use `hmac.compare_digest()` for string comparisons involving secrets, tokens, or hashes to enforce constant-time evaluation. When validating payload signatures in FastAPI, always extract the raw bytes via `await request.body()` instead of the parsed JSON object. In API endpoints with broad exception handlers, explicitly catch and re-raise `HTTPException` before the general `Exception` block to ensure security-related HTTP status codes are correctly propagated rather than swallowed into a false success state.

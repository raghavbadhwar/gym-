## 2026-03-25 - Fail Secure Webhook Error Handling & Timing Attacks
**Vulnerability:** The WhatsApp webhook endpoints (`/api/v1/webhooks/whatsapp`) were lacking webhook payload signature validation, making it vulnerable to spoofing. Furthermore, the GET verification endpoint was vulnerable to timing attacks due to normal string comparison for the `hub.verify_token`. In the POST endpoint, the general exception handler was swallowing raised exceptions, meaning if a security exception like 401 Unauthorized or 500 Internal Error were raised, it would be caught, logged, and a 200 OK status code would be mistakenly returned to the webhook sender.
**Learning:** When adding security checks to FastAPI/Starlette webhooks that require returning explicit HTTP errors, general `Exception` handlers (which are often added to "prevent Meta from retrying") will catch explicit `HTTPExceptions` and swallow them, bypassing intended fail-secure mechanisms. Additionally, normal string comparison leaks secret lengths over time.
**Prevention:** Always use `secrets.compare_digest` or `hmac.compare_digest` to check webhooks tokens to prevent timing attacks. In webhook handlers where a 200 OK must generally be returned on processing errors, explicitly catch and re-raise `HTTPException` before general `Exception` handling to ensure 401s, 403s, and 500s are correctly returned for fail-secure validation.
